Bank Partner API Requirements — Wallet & Payments

For bank integration team · August 2026 · Confidential

GH Trust MFB is building a digital wallet for customers on mobile and web. We are seeking a bank partner to provide the payment APIs below so we can fund wallets, pay out to customers, disburse loans, and collect repayments — all under CBN MFB regulations.

What we need from you: REST APIs (JSON), sandbox environment, webhooks for real-time events, and production credentials. Our platform already integrates similar rails (Monnify, Paystack, Zest); we will build a dedicated adapter for your bank’s API specification.

2. End-to-end flows (what your APIs must support)

2.1 Customer signup → wallet ready

  1. Customer completes registration (BVN, name, phone verified).
  2. We call your API to create a reserved / dedicated NUBAN linked to the customer.
  3. Customer sees account number and bank name in the app.
  4. Webhook confirms account is active (if async provisioning).

2.2 Fund wallet

  1. Customer transfers NGN from any bank to their wallet NUBAN.
  2. Your system sends inbound payment webhook with amount, reference, payer details.
  3. We credit customer wallet (idempotent on your transaction reference).
  4. Optional: requery API if webhook is delayed.

2.3 Withdraw to bank

  1. Customer requests withdrawal; we lock the amount internally.
  2. We call your single transfer / NIP disbursement API with bank code, account, amount, unique reference.
  3. Webhook reports success, failure, or reversal.
  4. We settle or release the locked balance accordingly.

2.4 Loan disbursement (admin)

  1. Loan approved in admin portal with amount and customer bank details.
  2. Ops initiates disbursement — same transfer API as withdrawal, different narration/metadata.
  3. Success webhook → loan marked disbursed in our system.

2.5 Loan repayment (Phase 2)

  1. Option A: Customer pays into wallet NUBAN; we allocate to loan balance internally.
  2. Option B: Customer pays into loan-specific collection account; webhook credits loan.
  3. Option C: Direct debit mandate debits salary account on due date.

3. Required bank APIs — complete list

Priority key: P1 = required for wallet go-live · P2 = loan collections & fees · P3 = nice to have

A. Authentication & environment

A1. API authentication

P1 · OAuth2 client credentials or API key + secret with short-lived bearer token
  • Token endpoint returning access_token and expires_in
  • Sandbox and production base URLs
  • IP allowlisting option for webhooks and API calls

A2. Merchant / MFB settlement account setup

P1 · One prefunded settlement wallet for outbound transfers
  • Settlement account number provided at onboarding
  • Contract / merchant ID we pass on all collection and disbursement calls

B. Customer wallet accounts (inbound collections)

B1. Create reserved / dedicated virtual account

P1 · Permanent NUBAN per customer

We send:

  • account_reference — our unique customer ID (immutable)
  • account_name — e.g. "GH Trust / {Customer Name}"
  • customer_email, customer_name, phone
  • bvn — where regulation requires BVN-linked accounts
  • currency — NGN

You return:

  • account_number (10-digit NUBAN)
  • bank_name, bank_code
  • account_reference (echo or your ID)
  • status — active / pending

B2. Get reserved account details

P1 · Lookup by account_reference

Same fields as B1. Used for reconciliation and support.

B3. Create dynamic virtual account (optional)

P2 · Temporary NUBAN for specific amount + expiry

We send: amount, currency, customer_email, transaction_reference, expiry_minutes

You return: NUBAN, bank name, amount, expiry timestamp, tracking reference

B4. Deactivate / suspend virtual account

P2 · Fraud, account closure, KYC failure

C. Inbound payment notifications & verification

C1. Webhook — inbound transfer received

P1 · Real-time; HMAC-signed payload

Minimum payload fields:

  • event_type — e.g. payment.success
  • transaction_reference — your unique ID (idempotency key)
  • payment_reference / session reference
  • amount, currency, payment_status (PAID / FAILED)
  • account_reference and/or destination_account_number
  • paid_at timestamp
  • Optional: payer bank, payer account (masked), narration

We respond HTTP 200; retries with exponential backoff on non-2xx.

C2. Verify / requery inbound transaction

P1 · GET by transaction_reference or payment_reference

Returns amount, status, account reference, timestamps. Used when webhook is missed (we poll every 2 hours).

C3. Requery virtual account payments

P2 · By account number + date range

Recovery of missed credits for a customer NUBAN.

D. Outbound transfers (withdrawals & loan disbursement)

D1. Bank account name enquiry (NIP validation)

P1 · Before saving payout account or disbursing

We send: account_number (10 digits), bank_code (NIP code)

You return: account_name, account_number, bank_code

D2. List supported banks

P1 · For bank picker in app

Returns bank name, NIP bank code, slug. Updated list or static file acceptable.

D3. Initiate single bank transfer

P1 · Withdrawals + loan disbursement

We send:

  • reference — our unique idempotency key (required, max 64 chars)
  • amount (NGN, 2 decimal places)
  • bank_code, account_number, account_name
  • narration — e.g. "GH Trust wallet withdrawal" / "Loan disbursement LOAN-1234"
  • currency — NGN

You return: reference, status (pending / processing / success / failed), transaction_id

D4. Verify outbound transfer status

P1 · GET by reference

Returns final status, failure reason, session ID, completion time.

D5. Webhook — outbound transfer result

P1 · Required events:
  • transfer.success — completed
  • transfer.failed — failed with reason
  • transfer.reversed — reversed after success

Payload must include our reference, amount, status, transaction_id.

D6. Bulk bank transfer

P3 · Batch loan / school payouts

Submit array of transfers; batch reference; per-item status in response/webhook.

D7. Transfer recipient registration (optional)

P2 · Pre-register beneficiary for faster repeat payouts

If your platform requires beneficiary tokens, provide create + fetch recipient APIs.

E. Treasury & settlement

E1. Settlement wallet balance

P1 · Available balance for disbursements

Returns available_balance, ledger_balance, currency. Used before large disbursement runs and daily treasury checks.

E2. Settlement account statement

P2 · Date-range transaction list for reconciliation

P2 · Salary account direct debit (Payday product)

You return / webhook: success, insufficient funds, mandate cancelled

F4. Cancel / suspend mandate

P2

G. Alternative funding channels (Phase 3)

G1. Initialize card / USSD / QR payment

P3

Returns payment URL or USSD code; amount, reference, customer email.

G2. Webhook — card/USSD payment success

P3 · Same fields as C1 inbound webhook

H. KYC & compliance

H1. BVN-linked account provisioning

P1 · If required by CBN for dedicated accounts

4. Webhook specification (summary)

EventWhenPriority
Inbound payment successCustomer funds wallet NUBANP1
Reserved account activatedDVA provisioning completeP1
Reserved account failedProvisioning rejectedP1
Outbound transfer successWithdrawal or loan disbursement paidP1

Mandate activated / failedDirect debit setupP2
Direct debit collected / failedRepayment attemptP2

Webhook requirements

  • HTTPS POST to our endpoint (we provide URL per environment)
  • HMAC signature header (SHA-256 or SHA-512) over raw body
  • Unique event / transaction ID for idempotency
  • Retry policy: at least 24 hours with backoff
  • Static IP list for firewall allowlisting (optional)
